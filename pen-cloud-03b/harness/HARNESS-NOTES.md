# PEN-CLOUD-03-B acceptance harness

Measures the arms of the experiment (A Relume React control, B Penpot code output, B' React variant, C Foundation Studio generated, C-SSR) against the same routes, viewports and thresholds. Built to the contract in `../ARM-CONTRACT.md`; token ids, tiers and sweep boundaries come from the DSC selected with `--dsc` (default `../inputs/dsc/fs.ds.relume-default.r3.json` when it exists, else `...r2.json`), copy from `../inputs/copy.json`.

## Setup and run

```sh
cd harness
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 pnpm install --frozen-lockfile   # @playwright/test pinned to 1.56.1 -> Chromium 1194 in /opt/pw-browsers
pnpm run harness -- --arms A,B,Bp,C,Cssr --out ../results/run-<label>
pnpm run harness -- --dry-run                     # stub arms + fixtures, no real arm needed (~4 min for 3 arms)
node summarise.mjs ../results/run-<label>         # regenerate summary.json / summary.md from a run dir (criteria r3)
node summarise.mjs ../results/run-r2 --criteria r3 --out .tmp/x   # re-judge an older run without touching it
```

Pinned: `@playwright/test 1.56.1`, `pixelmatch 8.0.0`, `pngjs 7.0.0`, `@axe-core/playwright 4.14.0`, `ssim.js 3.5.0` (lockfile committed). Do not run `playwright install`.

Options: `--criteria r1|r2|r3|r3.1` (default `r3` (OD-51), see below; `r3.1` is the OD-47 amendment, last section; `node summarise.mjs <dir> --criteria r1` re-judges an existing run with the original wording; when the criteria differ from the ones the run was recorded under, `summarise` writes `summary-<criteria>.{json,md}` instead of overwriting; `--out <dir>` writes elsewhere), `--dsc <path relative to ../inputs>` (default `dsc/fs.ds.relume-default.r3.json` if present, else `...r2.json`; used by `loadDsc()` everywhere - token compare, `?bp=` tiers, sweep widths - and recorded in `run.json` as `dsc`/`dscRevision`), `--frozen <file>` and `--verify-script <name>` (determinism overrides, see D-7), `--select-only` (print the determinism selection for the arm-c tree on disk, run nothing), `--steps build,pages,responsive,scroll,visual,determinism,licence` (default: all except licence), `--licence` (adds the licence step), `--skip-build`, `--routes r1,r2` (debug subset of the per-page measurements), `--no-summary`, `--label`. Arms run in the order A,B,Bp,C,Cssr regardless of the order given. Re-running with `--out` on an existing run dir adds to it (`run.json` keeps a `history`); that is how the licence step is run later: `pnpm run harness -- --steps licence --out ../results/run-<label>` (after C is frozen).

Per arm: `pnpm build` once per build group (A; B shared by B/B'; C shared by C/C-SSR; prefers `app/` when it has a build script, else the arm root) -> start server (the arm must define the script and listen on its contract port by itself; A `pnpm serve` in `/home/user/pc03b-arm-a/app`; B `pnpm serve` and B' `pnpm serve:react` in `../arm-b`; C `pnpm serve` and C-SSR `pnpm serve:ssr` in `../arm-c`) -> wait for the port (90 s) -> measure -> kill the server's process group. A port already serving before start aborts that arm (`error.json`). Arms B/B' are requested with `?bp=tablet` (768) and `?bp=mobile` (375); sweep widths map via the DSC `breakpoints` tiers (r1/r2: >=1024 none, r3: >=992 none; >=768 tablet; else mobile; the `screens` array never affects `?bp=`). Browser: Chromium headless, deviceScaleFactor 1, `en-GB`, `UTC`, light, `reducedMotion: no-preference` (the reduced-motion check uses a fresh context).

## Definitions and assumptions worth knowing

- **Section location** (page route, and column heuristics): each section is found by its copy text (`inputs/copy.json` headings, first `nav` for the navbar) and grown to the largest ancestor containing no other section's anchor. Works for every arm because the copy is identical.
- **Semantic score**: expected roles per route (`navbar` nav+1 button; `header80` h1+2 buttons; `layout620` h2+3 h3+1 button+1 link; `testimonial37` h2; `cta25` h2+2 buttons; `button` 2 buttons; `page` = per-section expectations + exactly one h1). Score = sum(min(actual, expected)) / sum(expected). Roles are computed (explicit `role` else implicit by tag; `<a href>` = link). A Relume link-variant `<button>` therefore counts as a button, not a link. Role-tree equality to A compares `tag|role|level|text` over the whole list (`visibleTreeEqualA` is also recorded).
- **Scroll probe**: "section" = the nearest ancestor of the sticky stage that is taller than the stage (falls back to the subject root when nothing is sticky, e.g. Arm B); the target is `top + p*(height - innerHeight)` using the absolute top. Animation threshold compares `translateY / offsetHeight` (percent of the column height) of each arm against A, tolerance 2 percentage points.
- **Token integrity**: only declarations on governed properties (colour, background-color, border-*-color, font-size, padding*, gap/row/column-gap, border-radius, line-height, font-weight, font-family) in rules whose selector matches the page, inside currently-applying `@media`/`@supports`, plus inline `style` attributes. Classes: `var` (contains `var(--fs-`), `literal`, `otherVar` (a bare non-`--fs` var()), `neutral` (inherit, currentColor, transparent, none, normal, auto, 0). `boundShare = var/(var+literal)`; `boundShareStrict` also counts `otherVar` as unbound. Union over all routes/viewports. DSC var names are resolved by squashing separators and case (`fs.token.color.scheme.text` matches `--fs-color-scheme-text` or `--fs-token-color-scheme-text`); values are normalised (hex/rgb, rem->px, quotes, spaces).
- **FROZEN parsing**: any line containing a 64-hex SHA-256 and a path-like token is an entry (markdown table or plain list); when the file has a fenced block with hash lines (FROZEN-r2.md layout) only the fenced lines are entries and header lines such as `- generated-manifest.json sha256: <hex>` are reported as `headerHashLinesIgnored` (before this they produced a phantom "frozen but not on disk" entry, so no file in that layout could ever pass); legacy `frozen` block files are matched by path suffix. If the real FROZEN.md uses another format (e.g. one aggregate hash), `frozen.aggregateFound` tests a SHA-256 over sorted `path hash` lines and the summary will show a FAIL with the unmatched entries: adjust `parseFrozen` in `src/determinism.mjs`.
- **Sweep widths** (`config.mjs sweepWidths(dsc)`, rule since r3): the 64-px series 375, 439, ... 1399 plus 1440, united with every `screens[].minWidth` and every `breakpoints[].minWidth` of the selected DSC and each of those minus one, clipped to [375, 1440], sorted unique. r2 DSC: 375 439 503 567 631 695 759 767 768 823 887 951 1015 1023 1024 1079 1143 1207 1271 1335 1399 1440. r3 DSC: adds 479 480 767 768 991 992 1279 1280 1439 (and drops 1023/1024). The list is recorded in `run.json` and `responsive.json`; the viewport set of the page/scroll steps (1440/768/375) and the sweep height (900) are unchanged.
- **Licence step** is supplementary evidence, not proof. It reads `/home/user/pc03b-arm-a/relume-src` only to hash trimmed lines >= 40 chars. The forbidden strings are assembled at runtime so this harness never contains them.
- Axe runs with default rules on the loaded page (no tag filter); the pass criterion counts serious+critical only.

## Dry run

`--dry-run` builds its arm-c fixture from the DSC generations present under `../inputs/dsc` (one `FROZEN*.md` per generation with the matching `DSC revision:` line, a stale hash in every file but the active one, a `generate:verify[:rN] --dsc ...` script per generation, manifest `dsc.revision` = the active DSC), writes a temporary r3-shaped DSC under `harness/.tmp/` for the `--dsc`/sweep tests and deletes it, then `--dry-run` starts in-process stub servers on ports 4391..4395 (plain page for A, static-columns page honouring `?bp=` for B/B', `--fs-*` token page with `data-fs-*` for C/C-SSR), builds fixtures (a tiny `arm-c` with `generate:verify`, `build`, `FROZEN.md`, and a fake `relume-src` sharing one planted line), runs every step, runs `summarise`, then asserts ~140 invariants (`dry-run-assertions.json`). Output goes to `harness/.dry-run-out/` (git-ignored). The stub arms are not a reference implementation: their PASS/FAIL in `summary.md` is meaningless.

## Acceptance criteria r1 / r2 / r3 (default r3); r3.1 is an amendment, see the last section

The r2 section below is the specification change recorded after run r1; r3 is described after it. All measurements record the data for both; `--criteria` only selects how `summarise` judges (r1 = original wording, kept available).

1. **Semantic**: required = SAC-expected roles 100% present at every viewport. Role tree vs A is an informational row. `summary.md` has an "A reference anomalies" section (A's own semantic score < 1 and its serious/critical axe hits) so they are not read as C defects.
2. **Token integrity**: `boundShare` is over DSC-governed declarations. For C/C-SSR the harness reads `<arm-c>/app/src/generated/generated-manifest.json` `ungoverned[]` (`{file, property, value, reason, source}`). A literal is excluded when file basename + property + normalised value match (`excludedStrict`); if the stylesheet is not identifiable as any manifest file (e.g. a hashed bundle) property + value alone match (`excludedLoose`, reported separately). Literals not covered are `uncoveredLiterals`, the real failures. The raw share stays as information (`boundShare`, `rawBoundShare_info`). Non-governed properties (`border-width`, `height`, `max-width`, `margin-top`) are never counted; `padding-inline` is governed and is excluded only via a manifest entry. Empty values left in `cssText` by `var()` shorthands are counted as `unreadableValueDecls`, not as literals.
3. **Responsive padding**: measured as `sectionPadding[key]` on the nearest `<section>` containing the route heading (navbar: the `<nav>` or the element holding the first nav link), else the nearest `data-fs-id` section root (`fs.section.<a>.<b>`), else the nearest `header`/`nav`; not on the `data-fs-subject` wrapper. Sections for which A has no element are skipped. Data from an r1-era run lacks `sectionPadding`, so r2 reports MISSING for it until re-measured.
4. **Determinism**: `determinism.json` has `frozenRoot` (hashes of `app/src/generated/**` and `generator/**` keyed by arm-c-root-relative path vs every FROZEN.md entry, exact path match; unlisted files are informational). The old `frozen` block (generated-dir-relative) is kept for r1.
5. **Licence**: lines that are pure `import`/`export ... from` statements are counted separately (`importLineMatchCount`, `importLineMatches`); r2 passes on `matchCountExclImports === 0`; `matchCount` is the r1 total.

## Criteria r3 (default)

Identical to r2 except for two corrections of the harness (not of the thresholds) found in run r2, plus the sweep rule. Measurement records the data needed by all three; `--criteria` only selects how `summarise` judges. A run recorded under r2 can be re-judged under r3 where the stored data allow it (D-6) and not where they do not (D-7).

### D-6: token-integrity accounting (`src/tokenrules.mjs`)

r2 left two kinds of literals uncovered in Arm C, giving a governed share of 94.85% (92 / (92 + 5)): zero resets (`padding: 0px` in `Navbar.css`, `base.css` `ul` and `.fs-sr-only`, `Testimonials.css`) because the browser serialises `0` as `0px` and the neutral list only knew `0`; and `padding: 0 24px` (`Button.css`), whose horizontal 24px the manifest lists as `padding-inline: 24px`. r3 accounting:

1. **Zero lengths are neutral**: `0`, `0px`, `0rem`, `0em`, `0%`, `-0px`, other zero lengths, and any multi-value whose every component is a zero length (`0 0`, `0px 0em`).
2. **Shorthand/longhand-aware coverage** of the governed box properties. A declaration is expanded to axes (physical, LTR: inline = left/right, block = top/bottom) and covered when each non-zero component equals the value of a manifest entry on the same axis: `padding-left`/`-right` by `padding-inline` (or `padding-left`/`-right`, or a `padding` shorthand's horizontal component), `padding-top`/`-bottom` by `padding-block` (or the vertical component), `row-gap`/`column-gap` by `gap`, `border-*-radius` by `border-radius`, and the reverse (a `padding`, `gap` or `border-radius` shorthand is covered when each non-zero component is). Values are compared normalised (`1.5rem` = `24px`). `var()`/`calc()` values and elliptical `a / b` radii are not expanded. The strict (same file basename) and loose (stylesheet not identifiable, e.g. a hashed bundle) scopes are kept: a shorthand hit in a file the manifest knows must come from that file's entries, otherwise from any entry.

`token-integrity.json` `arm_level.governed` holds the r3 numbers: `coverage: {strict, loose, viaShorthand, uncovered}` (over the literals that remain after the zero rule), `viaShorthandScope`, `zeroLengthNeutral`, `excludedByManifest` (= strict + loose + viaShorthand), `uncoveredLiterals`, `boundShareGoverned`, `rule: "r3"`. `governedR2` keeps the r2 accounting so `--criteria r2` is unchanged on new data. The raw browser classes (`literalDecls`, `neutralDecls`, `boundShare`) are not changed: r1/r2 numbers stay reproducible. `rawLiterals` (complete union) and `manifestEntries` make a stored run self-contained for re-judging. Per page: `boundShareGoverned` (r3) and `boundShareGovernedR2`.

**Re-judging a run recorded before r3** (`node summarise.mjs ../results/run-r2 --criteria r3 [--out <dir>]`): possible when `literalSamples` holds every literal (count equals `literalDecls`, true for run r2: 20 of 20) and a copy of the manifest the run measured is available. The manifest is accepted only when its sha256 equals the one the run recorded (`C/determinism.json` `generated.hashes["generated-manifest.json"]`); candidates are `--manifest`, the recorded path, `<run>/C/generated-manifest.json` and `harness/rejudge/<run dir name>/generated-manifest.json`. `harness/rejudge/run-r2/generated-manifest.json` is a byte-identical copy of the r2 manifest (sha256 ca252861...; it equals `arm-c/FROZEN-r2.md`'s entry) recovered after `arm-c/app/src/generated/` was regenerated for r3. Per-page rows of a re-judged run are derived from the union (every page literal is in it, so 0 uncovered in the union means 100% per page). If the manifest cannot be found or does not match, the rows are MISSING with the reason; nothing is guessed.

### D-7: choosing the FROZEN file and the verify script (`selectDeterminismInputs`)

The r1/r2 harness hard-coded `pnpm generate:verify` and `FROZEN.md`, so run r2 compared r2 output with r1 hashes. Now:

- `manifestRevision` = `<arm-c>/app/src/generated/generated-manifest.json` `dsc.revision` (read before anything runs);
- `frozenFile` = the `FROZEN*.md` in the arm-c root whose `- DSC revision: sha256:...` line equals it (several matches: last in natural order, with a warning);
- `verifyScript` = among the `generate:verify*` entries of `<arm-c>/package.json` `scripts`, the one whose `--dsc <path>` (path relative to `../inputs`; `--dsc=<path>` also parsed) names a DSC file whose `revision` equals it. Fallback `generate:verify` when no script carries `--dsc`, or none verifies that revision (the bare script uses the generator's default DSC; this case is warned);
- `--frozen <file>` (relative to the arm-c root or absolute) and `--verify-script <name>` override and are recorded as such. `node src/cli.mjs --select-only` prints the selection for the tree on disk;
- recorded in `determinism.json` as `frozenFile`, `verifyScript`, `manifestRevision`, `selectionBasis {frozen, verifyScript}`, `selection {ok, candidates, warnings, harnessDscRevision, manifestMatchesHarnessDsc}`; printed in the summary (a "Determinism inputs" line, an info row and the verify/FROZEN row values). If no FROZEN file carries the manifest revision, the FROZEN row FAILs with that reason.
- A r2-era `determinism.json` has no selection fields: under r3 its two required rows are MISSING ("re-run the determinism step"), because they were computed against the wrong generation; they are not re-judged from partial data.

### Other r3 points

- Sweep widths include the DSC `screens`/`breakpoints` boundaries (see "Sweep widths"). The responsive threshold wording says so; pass/fail logic is unchanged.
- `--dsc` selection never changes `bpForWidth`'s source: tiers come from `breakpoints`, so with the r3 DSC (`lg` 992) Arm B receives `?bp=tablet` for 768..991 and none from 992.

## Criteria r3.1 (amendment under OD-47)

Separately versioned amendment: `--criteria r3.1` = criteria r3 plus one change to how the forbidden-string hits are judged (not to how they are found). The default stays `r3` (OD-51); r3, r2 and r1 judge exactly as before (any forbidden-string hit fails). Selectable in `src/cli.mjs` and `summarise.mjs` (`node summarise.mjs <run> --criteria r3.1` writes `summary-r3.1.{json,md}` when the run was recorded under another criteria set). Owner ruling OD-47: third-party identifiers are permitted in designated provenance fields only; build-script occurrences are inspected separately; package names are not broadly allow-listed; dependency/source checks are not weakened; the original R3 FAIL stays as recorded.

**Rule.** Detection is unchanged: all three runtime-assembled patterns are scanned over the whole experiment dir, every hit is detected and listed, patterns 1 and 3 and the line-hash comparison are untouched, no pattern is removed or relaxed and no package name is allow-listed (the exemption is by field designation, not by string). Each hit (file x pattern) gets a `classification`:

1. `provenanceField` when the file is a `.json` file and every occurrence of the matched string in that file lies inside the string value of a key named `provenance` or `screensProvenance` or ending in `Provenance`, at any depth. The file is parsed and the occurrences are located by walking the values (no regex on the raw text for the decision). Only a string held directly by such a key qualifies (an array or object under it does not); an occurrence in a key name or in any other value makes the file `other`; the walked count must also equal the raw occurrence count, otherwise (escaped forms, duplicate keys, unparseable JSON) the file is `other`.
2. `builderAssignment` when the file is under `scripts/` with a `.py`, `.ts`, `.mjs` or `.js` extension and every line containing the string is an assignment or dictionary entry whose key name is `provenance`, `screensProvenance` or ends in `Provenance` (`'screensProvenance': '...'`, `screensProvenance = "..."`, `d["xProvenance"] = '...'`, `const yProvenance = '...'`). The value must be a single string literal (optional trailing `,`/`;`/comment), so a second statement on the same line or an expression does not qualify. The line numbers are recorded (`lines`).
3. `other` for everything else: markdown notes, source files, generated files, lockfiles, package manifests, files outside `scripts/`, and any JSON or script with at least one occurrence that is not in a designated field or assignment line (the offending lines or JSON paths are recorded).

**Judgement.** Under `--criteria r3.1` the forbidden-strings row passes only when every hit is `provenanceField` or `builderAssignment`; a single `other` hit fails it. The row value lists every hit with its classification (and the JSON field paths / builder line numbers, or the reason for `other`), the counts per class, and `classificationSource`. `licence.json` `forbiddenStrings.hits[]` now carry `classification` and its detail, plus `classificationCounts`; runs recorded before r3.1 (e.g. run r3) have no classification in the stored hits, so `summarise` re-derives it from the files on disk under the stored `root` at summarise time and says so in the row (`classificationSource`: the files may have changed since the run; a file that cannot be read is `other`).

**Scope (informational).** Every `other` hit also carries `scope`: `frozenPriorRevision` when the file is a DSC JSON (`inputs/dsc/fs.ds.relume-default.r<N>.json`), DSC notes file (`DSC-R<N>-NOTES.md`) or builder script (`scripts/build-dsc-r<N>.*`) whose revision number N is lower than the revision the run's arm-c manifest `dsc.revision` points at (matched against the `revision` fields of the DSC files; recorded in `determinism.json` `manifestRevision`), and `current` otherwise, including when the manifest revision matches no DSC file. The counts of `other` split by scope are in `classificationCounts.otherByScope` and in the row value (`counts.otherByScope`, also under r3 as `informational`), so frozen earlier inputs and current files can be told apart; scope never changes pass/fail, and a single `other` hit fails the row under r3 and r3.1 whatever its scope.

**Run r3 hits.** The scan of the tree on disk finds, per hit, that `inputs/dsc/fs.ds.relume-default.r3.json` has the string in `screensProvenance` and also in four `changeLog[].evidence` values, that `scripts/build-dsc-r3.py` has the `'screensProvenance'` entry (line 74) and also four changelog lines (65 to 68), and that `inputs/dsc/DSC-R3-NOTES.md` is markdown. By the rule above all three are therefore `other`, and r3.1 does not turn the run r3 forbidden-strings row from FAIL to PASS unless those files change. The recorded R3 FAIL is not altered; r3.1 summaries are separate files.

`pnpm run dry-run` exercises both classifications, the mixed/negative cases and the row judgement under r3, r2 and r3.1 with fixtures assembled at runtime (the harness still never contains a forbidden string literally).
